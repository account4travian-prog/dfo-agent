## What the best guides do — 12 patterns

### 1. A quest index grouped by *who gives the quest*, not by alphabet
UESP's Daggerfall quest page is the strongest benchmark for DFO: 227 quests under 14 giver/faction headings, each line a **hook sentence** (who, what) rather than just a title ([source 5](https://en.uesp.net/wiki/Daggerfall:Quests)). OSRS and BG3 wikis do the same at different granularity (quest list by area/difficulty, act → questline). The index is the search landing page and the browse page at once. **For DFO:** the quest guide needs one `Quests` index grouped exactly the way the game hands quests out — introduction questlines, NPC-guild quests, player-guild quests, town/board work, story lines, seasonal events — with giver, gate and stage page on each row.

### 2. Quest pages have a *fixed header block of facts* before any prose
UESP's `Quest Header` asks for Giver, Reward, Prev, Next, Loc, Image, Icon and a one-phrase description ([source 1](https://en.m.uesp.net/wiki/UESPWiki:Style_Guide/Quest_Layout)); OSRS's quick guide has a details table with start point (plus **Show on map**), difficulty, length, requirements, items and enemies ([source 3](https://oldschool.runescape.wiki/w/Cook%27s_Assistant/Quick_guide)). This is the "can I do this quest now, and what do I get?" test answered in five seconds. **For DFO:** a `Quest facts` box: giver and where, gate (level/Renown/registered/questline step), prerequisite quests, rewards (Marks/gold/items/Renown/profession), shareable/party behaviour, and a link to the map pin.

### 3. The dual-layer page: a numbered quick path and a detailed walkthrough
UESP mandates a **Quick Walkthrough as a numbered list** with "as few spoilers as possible", then a **Detailed Walkthrough** in paragraphs with `===` subheadings for the choices and dialogue ([source 1](https://en.m.uesp.net/wiki/UESPWiki:Style_Guide/Quest_Layout)). OSRS splits them into two pages — a `Quick guide` and an in-depth guide, cross-linked both ways ([source 3](https://oldschool.runescape.wiki/w/Cook%27s_Assistant/Quick_guide)). The quick layer is what returning players use; the detailed layer is what first-timers use, and the split lets each stay short. **For DFO:** every quest page gets "At a glance" → **Quick path** (6–10 numbered steps, spoiler-light) → **Detailed walkthrough** with a subsection per step; a quest that is small can keep both on one page.

### 4. Explicit choice/consequence and failure-recovery sections
UESP's guidelines demand that "any time you are given alternatives... the walkthrough should specify what the alternatives are, any conditions that need to be met... and the consequences of each choice"; bugs get their own consistently-titled section so other pages can link to it ([source 1](https://en.m.uesp.net/wiki/UESPWiki:Style_Guide/Quest_Layout)). OSRS adds "Required for completing" (what this unlocks) and a transcript ([source 2](https://oldschool.runescape.wiki/w/RuneScape:Style_guide/Layout)); Game8 marks **"point of no return"** warnings inline ([source 8](https://game8.co/games/BG3/archives/419608)). **For DFO:** "Choices" table (what each changes), "If it goes wrong" (held step, missed window, death, NPC not there, quest item lost), "Bugs" with a stable anchor, "Unlocks later" — these are exactly the failure-recovery gaps the writing audit flagged for the rest of the handbook.

### 5. Data-derived sections are generated, not hand-maintained
UESP's quest "Journal Pages"/"Quest Stages" sections "have been generated by scripts that can read the game data files, and do not need to be manually created" ([source 1](https://en.m.uesp.net/wiki/UESPWiki:Style_Guide/Quest_Layout)); OSRS's drop tables, rewards and quest-details templates are consistent because data lives in templates ([source 2](https://oldschool.runescape.wiki/w/RuneScape:Style_Guide/Layout)). The handbook already has this instinct (`{{fact}}` + facts pipeline). **For DFO:** extend the same approach to quest data: gate/level/Renown from `qlLines.js`, start NPC and rewards from the quest machine, flags (registered/online/feature), and a generated "quest facts" block on every quest page; hand-write only the walkthrough and the judgement calls.

### 6. Versioned, dated freshness is visible at the point of use
Every benchmark surfaces freshness: UESP's "last edited" footer and history; OSRS's "last modified" and Recent Changes; BG3 wiki's "Latest BG3 update: Small Hotfix – 17:03, 29 September 2026"; PoE's "Latest version 3.29.3b — September 4, 2026" plus version history ([sources 2, 4–7](https://oldschool.runescape.wiki/w/RuneScape:Style_guide/Layout)). Wowhead goes further, serving separate Live/PTR versions of the same guide (source 10). Game8's stale "Last updated: September 7, 2023" is the counter-example ([source 8](https://game8.co/games/BG3/archives/419608)). **For DFO:** the new "How this guide is checked" page is the right foundation; quest pages should show a per-page "checked against build/date" line at the top (not just the footer) and a per-quest "since sync" changelog when a quest changes.

### 7. Hub pages are maps of intent, not lists of links
BG3 wiki's main page is a grid of *player intents* (Gameplay, Character creation, Act overview, Mechanics, Characters) with counts and a "latest update" strip; PoE's is Equipment/Itemisation/Crafting/Exiles/The world/Skills; UESP's is per-game. All are **task-oriented**, not alphabetical ([sources 6–7](https://bg3.wiki/)). **For DFO:** the quest guide needs a hub at two levels: the handbook home gets a "Quests" tile, and `Quests` itself opens with "I want to… / start a questline / join a guild / find work / finish a step I'm stuck on / do the main story" rather than a raw alphabetical list. The quest index (pattern 1) sits below that.

### 8. Search is treated as a primary product surface, with structured entry points
All wikis expose search in the header and rely on long-tail query entry (quest names, NPC names, items). They help search by **redirects/templates and consistent naming**, by cross-linking named entities (a quest page links the NPC, the place, the item), and by creating structured pages for objects players search for (items, locations, NPCs). OSRS adds calculator/tool links; BG3 wiki links out to the best external tools (interactive map, dialogue browser, game-file search) rather than rebuilding them ([sources 2, 3, 6](https://oldschool.runescape.wiki/w/RuneScape:Style_guide/Layout)). **For DFO:** quest pages must be findable by the *player's* words, not the code's (giver name, town, reward, "stuck", "where do I start", aliases for questline names). Fix the search scorer (AND semantics, stop words, synonyms) before adding 30+ quest pages, or the new pages will be invisible.

### 9. Tables and checklists beat prose for repeat use
The evidence is everywhere in the fetched pages: OSRS item checklists and details tables; UESP's header/footer templates; BG3 wiki's quick-reference D&D table; Game8's objective tables. Tables compress comparison (which quest, which reward, which requirement) and checklists turn reading into doing. UESP's quest-layout page also insists on paragraph form for the detailed walkthrough — the lesson is **not** "tables everywhere" but "use the table for the facts, prose for the reasoning". **For DFO:** requirements/items/rewards/gates as small tables; a `[!checklist]` (the site already supports it) for "before you start" and "each step" on long quests; decisions as a choice table.

### 10. Maps are a retention product, not a nice-to-have
UESP's map tool publishes **10–15k views/day, 100k visitors/month and a 3:30 average visit**, and embeds maps into articles ([source 4](https://en.uesp.net/wiki/UESPWiki:Maps)); OSRS's details tables deep-link "Show on map"; BG3 wiki links Map Genie; Game8 sells interactive-map access as a membership perk ([sources 3, 4, 6, 8](https://en.uesp.net/wiki/UESPWiki:Maps)). Maps are where players return between quest steps. **For DFO:** the handbook already has an approved Bay/town map build — add quest **pins** (start NPC, objective, turn-in), filter by questline, deep-link `?pin=` URLs, and make the quest page's "where" line link to the pin. No game assets: the maps and markers are already the handbook's own.

### 11. Community/feedback loops create trust and coverage — and where they fail, communities leave
The best wikis are editable, with visible histories, style contracts, talk/discussion pages and Discord (UESP, OSRS, BG3 wiki, PoE). OSRS has "Active discussions", AutoWikiBrowser, a style-guide network; BG3 wiki tells editors their IP will be logged and invites them to Discord; PoE prominently asks for editors ([sources 2, 6, 7](https://www.poewiki.net/wiki/Path_of_Exile_Wiki)). The negative evidence is just as instructive: Wikipedia's Fandom article documents high-profile wikis migrating away over degraded functionality, ads and editorial interference ([source 9](https://en.wikipedia.org/wiki/Fandom_%28website%29)). **For DFO:** even a solo-authored handbook should ship the *feedback loop* now (the new "How this guide is checked" page + Discord + corrections page) and treat contributor entry (edit link, style guide, "good first quest") as a future step; the handbook already has the style contract, fact registry and validators to make outside contributions safe.

### 12. Mobile and accessibility are table stakes
Every benchmark offers a mobile route: UESP mobile site + Android app; OSRS "Mobile view" toggle; BG3 wiki's mobile layout; UESP's map "Improved mobile view & experience" ([sources 2–4, 6](https://en.uesp.net/wiki/UESPWiki:Maps)). Structural accessibility shows up in the contracts too: OSRS requires sections to be level-2 headings; UESP uses a fixed trail/header/footer structure; both give tables and lists real markup. **For DFO:** the handbook's stage/TOC/sidebar model is sound, but the writing audit found the in-page TOC disappears below 1200px and the glossary had an h1→h3 skip — fix those before adding a quest guide that will be mostly read on phones beside the game.

## Anti-patterns (observed or directly implied by the sources)

1. **The stale king.** A beautifully structured walkthrough whose "last updated" is years behind the live game (Game8's BG3 index, "September 7, 2023", source 8) actively trains players not to trust it. Freshness beats completeness.
2. **One giant page.** A single walkthrough that mixes quick steps, dialogue, choices, lore and bugs is skippable by returning players and intimidating to new ones; UESP/OSRS explicitly split quick vs detailed.
3. **Prose-only prerequisites.** Listing requirements inside a paragraph instead of a table/checklist makes the "can I start?" question a reading task (contrast OSRS's details table, source 3).
4. **Orphan pages and code-named titles.** Pages named after internal names, or with no inbound links from an index/hub, cannot be found by search or browsing; the handbook's own audit found 36/84 pages with zero body cross-links — a quest guide would multiply that.
5. **Unversioned rules.** Guides that don't say *which patch/commit* they describe are wrong the week after a balance change; Wowhead's Live/PTR split and BG3/PoE version strips exist precisely to avoid this.
6. **Ad-first, content-second.** The Fandom departures are the macro example: communities fork when ads/popups and platform priorities degrade reading (source 9). For a one-person handbook, the equivalent self-harm is autoplay/interstitial clutter and dead-end pages.
7. **Spoiler-blind writing.** Walkthroughs that open with the twist or the final reward reduce use for players who only need a nudge; UESP's "as few spoilers as possible" for the quick walkthrough is the rule to copy.
8. **Data duplicated by hand.** Numbers typed into prose instead of generated (the handbook audit's finding: facts used on 10/84 pages) guarantee drift; the wikis' script-generated quest-stage/drop sections are the fix pattern.
9. **No feedback path.** A public guide with no corrections route (or a route buried in a repo) loses the error reports that keep it accurate; the new checked page + Discord is the minimum.

## What predicts popularity and repeat use

Synthesizing the sources (and flagging this as inference, not measured):

1. **Coverage of the long tail.** Wikis win because every named quest/NPC/item has a page and a redirect; search engines and in-game confusion both point at long-tail pages. A quest guide that covers only the main lines will be out-competed by one that also covers guild chores, boards and seasonal lines.
2. **Time-to-answer.** The header/details block plus the numbered quick path gets a player from "what do I do" to "where do I click" in seconds; this is what makes a guide a *reference* rather than a *read*.
3. **Freshness within the patch cycle.** Version/date visibility at the point of use is the strongest trust signal; stale dates are the strongest negative signal.
4. **Return surfaces.** Maps (UESP's 3:30 average visit, 100k visitors/month), calculators, checklists and "what changed" pages create reasons to come back outside a walkthrough.
5. **Findability.** Search + hub + cross-links; a page that cannot be found does not exist. This is where the current DFO search (fails natural-language queries, no stage bias) and the chain-like link graph are the biggest risks to a new quest corpus.
6. **Low-friction reading.** Mobile-first layout, no ads/overlays, short paragraphs, tables for facts, stable anchors for "Bugs"/"Rewards"/"Walkthrough" so external links and the game's own community can deep-link.
7. **A visible community/feedback loop.** Editable wikis get corrected within hours; a solo guide needs an explicit correction path and a public changelog to get some of the same benefit.

## Recommendations for The DFO Online Handbook as it adds a quest guide

Prioritized against the current 101-page, source-checked handbook. Each is concrete enough to schedule.

### A. Quest IA (do first)
1. **Add a `Quests` hub** (new stage-like section or a reference-adjacent page) with intent entry points: "Start a questline", "Join a guild", "Find work on the boards", "I'm stuck on a step", "Main story order". Mirror the game's own cadence (the stage/questline ladder already in `STRUCTURE.md` and `reference/questline-ladder.md`).
2. **Add a quest index grouped by giver/faction**, UESP-style, one row per quest: name, giver + place, gate, rewards, and a one-line hook. This is the page search should land on; add filters by level/Renown/registered/questline.
3. **One page per quest** (or per questline with anchored per-quest sections if a line has 3+ quests), filed in the stage where the player first meets it — same progressive-disclosure rule the handbook already uses.

### B. Quest page template (append to `STYLE.md`)
4. **Fixed anatomy:** title → one-sentence summary → **Quest facts box** (giver, start location + map pin, gate, prerequisites, rewards, party/shareable, online-only flags) → At a glance → **Quick path** (numbered, spoiler-light) → **Detailed walkthrough** (`###` per step) → **Choices** table → **If it goes wrong** → **Rewards and unlocks** → **Bugs** (stable heading) → Next (line order) → Sources. This maps UESP's contract and OSRS's details/walkthrough/rewards/required sections onto the handbook's existing page anatomy.
5. **Dual layer:** keep the quick path and detailed walkthrough on one page while quests are short; split to `/quick-guide` only when a page exceeds ~1,500 words (OSRS pattern) so the ratio of page count to value stays sane.
6. **Generated quest facts:** pull giver/gate/rewards/flags from `qlLines.js` and the quest machine via the facts registry so the header can't drift; hand-write only walkthrough/judgement text. This is the single highest-leverage engineering choice for the quest corpus.

### C. Search and linking (before writing 30+ pages)
7. **Fix the search scorer** (the writing audit's F2): stop words, stemming, synonyms (`start/begin`, `join/apply`, `stuck/blocked`), apostrophe normalisation, FAQ answers as results, and stage-aware ranking. Add every quest name, giver name and location as indexed aliases.
8. **Cross-link both ways:** every quest page links the systems it touches (guilds, Renown, death, travel, Marks), and each system page gets a "Quests that use this" section. Enforce a minimum of 3 body links on quest pages in the checker.
9. **Stable anchors as a contract:** `#walkthrough`, `#choices`, `#bugs`, `#rewards` must exist on every quest page so the community, Discord pins and future game UI can deep-link them.

### D. Freshness and trust
10. **Per-page freshness at the top:** "Checked against build e4f093166 (25 Oct 2026)" rendered near the title on quest pages, plus a per-quest "changed in this sync" note when the facts diff touches it. Reuse `what-changed.md` and the facts snapshot; don't invent a second changelog.
11. **Standard "Bugs / known issues" section** with a stable heading and a link to the correction path (`how-this-guide-is-checked.md`, Discord), so errors are reported where they are found.
12. **Add a "quest data" section to What changed** each sync (new lines, changed gates/rewards, fixed quest bugs) — wikis' "Changes" sections are why readers trust updates.

### E. Maps and tools
13. **Quest pins on the approved map build:** start NPC/board, objective marker, turn-in; filter by questline; deep-link from the quest facts box ("where" line) and from the index; keep pins behind a spoiler toggle for main-story twists. UESP's map metrics show this is a repeat-use surface, not decoration.
14. **Checklists:** use the existing `[!checklist]` for "before you start" (items, potions, repair, bank) and long-quest step tracking; a checklist that persists in the browser is a reason to return.
15. **One original diagram per complex quest** (route sketch, puzzle layout, NPC relationship), under the existing no-game-assets/credits policy — the writing audit found zero in-article diagrams; quests are where they pay off most.

### F. Feedback/community
16. **Turn the new "How this guide is checked" page into a correction loop:** a one-click "report this quest" link (pre-filled page/commit) to Discord or an issue template, and a public "Corrections" list. Add contributor guidance for quest pages (the style contract + template) so outside help is safe.
17. **Track success:** candidate metrics — search queries that end in a quest-page click, % of quest pages with ≥3 inbound links, time-to-answer for the 20 top quest questions, repeat visits to the quest index and map, and the age of the oldest un-updated quest page after each sync. These are observable in the site's own analytics when it goes public; no external traffic tool needed.

## What not to copy for DFO

- **Don't copy wiki-scale community machinery** (talk pages, AWB, 30-editor governance) yet; copy the *contracts* (template, stable sections, freshness, correction path) that make community possible later.
- **Don't copy game-asset-heavy walkthroughs** (screenshots of dialogue, maps rendered from game data); the handbook is deliberately asset-free. Use original SVG diagrams, the approved map build, and terse prose.
- **Don't copy the ads/engagement layer** — the Fandom departures are the evidence that readers punish it, and the handbook's advantage is a clean, fast reading surface.
